# 规则写作指南

把用户的愿望转换为“触发条件 + Agent 动作 + 必要边界”。只写用户确认过的偏好，或 Skill 明示的核心原则。避免抽象赞美和没有操作后果的口号。

## 转写步骤

1. 找出用户想避免的行为或想得到的行为。
2. 写清触发条件：什么时候适用、什么情况例外。
3. 用可观察的动词描述 Agent 应采取的动作。
4. 保留用户原有的权限边界、优先级和适用范围。
5. 检查是否能用一次具体任务判断 Agent 有没有遵守。

## 示例

| 用户原话 | 不合格 | 可执行规则 |
|---|---|---|
| “别把事情搞复杂。” | 保持简单。 | 优先使用满足当前需求的最简单方案；新增依赖或引入新架构前，先说明必要性并征求同意。 |
| “别每次都问我。” | 更自主一点。 | 对可逆、低风险且目标明确的任务直接执行；会删除数据、对外发布或改变项目方向时先询问。注意：具体边界仍须用户确认。 |
| “说清楚点，我不太懂代码。” | 使用清晰语言。 | 首次出现的专业术语用一句话解释；先给结论，再用不超过三点说明代码改动及验证结果。 |
| “写完要确保没问题。” | 保证质量。 | 修改代码后运行与改动相关的现有测试；若无法运行，说明原因和未验证范围，不得称为已验证。 |
| “不要乱改。” | 小心修改。 | 只修改完成当前任务所需的文件；发现无关问题时先报告，不顺手重构。 |
| “我希望它能自己干。” | 全部自动完成。 | 在用户明确授权的范围内独立完成；遇到未授权的高影响操作或会改变目标的选择时暂停并询问。 |

## 约束

- 不把“用户没说”转成“用户允许”。
- 不把示例规则直接复制给用户；需确认具体偏好。
- 避免绝对词（总是、永远）造成无意的普遍授权；除非用户明确要求。
- 一条规则不要混入多个不相干动作。
- 长期规则写稳定偏好；单次交付要求留在当前任务，不写入 AGENTS.md。
