# 访谈框架

这份问题库供 `SKILL.md` 按需选用，不是问卷。先复用上下文，再挑尚未回答且会影响规则的问题。每轮最多 3–5 题；新手每轮最多 3 题。用户可自由回答或跳过。

## 第 1 轮：认识用户

开场后从这里开始：

1. 你主要做什么工作，或在做什么类型的项目？
2. 你平时怎么使用电脑或写代码？可以选：A 完全不会编程；B 能看懂一点；C 能改简单代码；D 能独立开发；E 专业开发者。也可以自己描述。
3. 你最常希望 Agent 帮你做什么？

如果是非技术工作，可询问产出类型或对象；不要追问代码能力细节。

## 第 2 轮：工作方式

自然地询问：“你更希望 Agent 怎么工作？”

- A. 做之前先告诉我准备怎么做，等我确认。
- B. 简单任务直接做，复杂修改先说方案。
- C. 尽量独立完成，只有关键选择或受阻时再问。

根据选项追问一个具体边界：哪些算简单/复杂/关键？例如“改一段文字”与“重写整个流程”。还可确认用户希望先看计划还是直接开始。不要要求用户理解“自主等级”等术语。

## 第 3 轮：沟通偏好

按需选 2–4 项：

- 你希望用中文、英文，还是跟随任务语言？
- 你喜欢先听结论还是先了解过程？回复简短还是详细？
- 解释代码时，需要逐步解释吗？术语要不要顺手说明？
- 如果你的方案明显有问题，你希望 Agent 怎么做？A 按方案执行；B 提醒风险后继续；C 说明问题并给更好的选项。

发现“总是简短”和“每次详细解释”等冲突时，请用户选适用场景或优先级。

## 第 4 轮：权限边界

必须确认具体动作。不要根据自主程度推断授权。可以先说明“我会把权限分成可直接做、先问你、明确不做三类”，再逐组询问。

按用户任务选择相关条目，每组最多问 3–5 个，分多轮：

| 动作 | 可供确认的边界 |
|---|---|
| 读取和搜索 | 读取项目文件、搜索资料/代码 |
| 创建与修改 | 新建普通文件、修改任务相关文件、批量修改 |
| 高影响更改 | 删除文件、大规模重构、改数据库/环境变量、安装依赖 |
| 外部操作 | Git 提交、推送、部署、发布、付费服务、向他人发送消息 |

用户无需确认每一项。记录“未问/未答”为未知或留空，不默认为允许或禁止。对于明显不适用的动作（例如非编码用户的数据库迁移）不要问。对高影响或不可逆操作，明确问“是否每次先征求你的同意”。

## 第 5 轮：技术环境（动态触发）

只有当用户实际做软件开发、让 Agent 改代码，或需要技术专属规则时才询问。一次挑最相关的几项：使用哪个 Agent/编辑器、操作系统、常用语言或框架、版本管理/运行方式。用用户熟悉的产品名提问；必要时解释术语。

内容创作、研究、资料整理等用户不进入这一轮。不要为填满 Profile 问 npm/pnpm、Docker、MCP 等无关问题。未知工具留空。

## 完成质量与输出

如果尚未覆盖，可询问：

- 任务完成后，Agent 至少要做什么检查或告诉你什么？
- 有什么情况必须明确标记为“还没完成”？
- 最终文件用什么语言、放在哪里？仅当目标路径不明确或可能覆盖文件时询问路径。
- 你主要在哪个平台使用这份说明？是当前项目生效，还是所有项目都生效？若已提到平台/范围则不重复问。可选 Codex、Claude Code、WorkBuddy、Cursor、GitHub Copilot、Windsurf、Gemini CLI、其他；支持多选。
- 你希望 Agent 在当前工作区直接保存，还是只给你内容和设置步骤？仅当当前环境有写文件权限时才提供“直接保存”选项。

“验证”“完成”需按用户任务具体化，例如文章需检查事实出处和字数，代码需运行相关测试或说明无法验证的原因。

平台问题用于决定最终文件格式和启用方式。用户若使用多个平台，先约定是否以 `AGENTS.md` 为主版本并生成兼容文件；不要把平台记忆、Skill 安装和项目规则混为一谈。平台与项目范围都不相关（例如只要一份可复制的通用说明）时，允许用户选择“只输出通用 Markdown”。

## 动态选择与冲突处理

每轮发送前检查：1）问题是否尚未回答；2）答案是否会改变最终规则；3）是否与用户工作相关。任一项为否则删掉问题。追问只用于消除会改变规则的歧义。

若用户说“任何操作都先问”又说“别打断我，全部自动做”，指出两句话的冲突，询问是否按风险区分，或让用户给出优先级；确认之前将相关权限保持未决，不生成冲突规则。

当 Profile 足以生成有用、无虚构的草案时停止追问，转入 Skill 中的生成前确认。不要为了填满字段而凑问题。
