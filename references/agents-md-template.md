# AGENTS.md 结构模板

按用户情况取用章节，未提供信息就删去对应章节；不要原样输出所有标题。用用户偏好的语言和称呼。

```markdown
# Agent 协作说明

## 关于我
- [与任务相关的身份、背景；避免隐私细节]

## 我通常做什么
- [常见项目和产出]

## 合作方式
- [自主范围、何时先讲方案、何时提问]

## 沟通偏好
- [语言、简洁程度、术语、分歧处理]

## 工作原则
- [只保留会改变 Agent 行为的原则]

## 权限边界
### 可以直接做
- [已确认]
### 做之前先问
- [已确认]
### 不要做
- [用户明确禁止]

## 技术偏好
- [仅编码用户：工具、语言、框架等已确认信息]

## 验证与完成标准
- [按任务类型说明检查方式和完成条件]

## 不确定时
- [何时提问、何时采用默认值以及如何标注]

## 更新本说明
- 当用户反复纠正同一种行为，或表达稳定的新偏好时，建议更新本文件。
- 不因临时任务要求改写长期偏好；更新前向用户说明变更。
```

## 章节组合

- **非编码内容创作者：** 身份、常见工作、合作方式、沟通、内容事实核查、发布权限、完成标准；移除技术偏好和代码测试。
- **用 Agent 做小工具的新手：** 仅当用户确实会让 Agent 改代码时采用此路径；使用少量术语并解释，只记录用户知道的工具；写清如何运行/检查工具及高影响权限。若用户不做编码，改用非编码路径，不因“新手”身份保留技术章节。
- **Vibe Coding 用户：** 规则应体现目标导向的自主执行：本地实现、检查和修正可连续完成；只有产品方向、不可逆改动、付费服务和上线等已确认的关键边界才暂停。不要擅自推断具体框架或授权部署。
- **专业开发者：** 优先记录用户给出的具体工程约定（如确切测试命令、格式规范、Git 操作边界）；没有提供时留空，不补入常见默认规范。跨模块计划、依赖升级、提交/部署边界按用户确认值书写。

输出通常 50–150 行；若删去无关章节后更短且完整，就保持短。不要保留空标题、占位符或示例中的答案。
